# T17 Copy-paste / clipboard detection on OnVUE

Scope: Can OnVUE detect/log/block clipboard copy-paste during an exam, and specifically — with the answer LLM on the HOST and OnVUE inside a **Type-1 hypervisor GUEST** — can OnVUE see a clipboard transfer **across the VM boundary**? Detection/feasibility level only; defensive. Grounding: T05 (OnVUE control surface), T06 (red-team inventory), T14 (Type-1 hypervisor). All web access dates **2026-11-12**. Convention: **BLOCK** = prevented; **LOG/FLAG** = recorded/reviewed; **UNKNOWN** = Pearson silent / not documented / unverified. Deployment assumption carried from T05/T14: **candidate screen is NOT shared or captured** — monitoring is webcam + mic + OnVUE client telemetry.

**Bottom line up front.** (1) Pearson documents a *policy* ban on copy/pasting exam content but documents **no technical clipboard monitoring, no paste/copy event logging, and no keystroke logging** in OnVUE; those remain **UNKNOWN**, so do not assume them. (2) With the screen unshared, the human proctor sees **nothing on-screen** — only the camera. (3) **OnVUE living inside the guest cannot see across the VM boundary**: it observes an ordinary local clipboard paste and has no guest-level visibility that the text originated on the host. (4) But there is a decisive structural tension: **host↔guest clipboard sharing requires hypervisor guest tools, and those same guest tools are a top-tier VM signature.** An attacker cannot easily have *both* a stripped/stealth guest (to beat VM detection) *and* automatic cross-boundary clipboard; stripping the tools forces a **manual** channel (retype, OCR-from-overlay, shared folder), which OnVUE also does not technically observe but which is slow and camera-visible. (5) Even with no VM, OnVUE is not documented to distinguish pasted from typed text; paste-event logging is a **web-page/exam-UI** capability that is trivially defeated by retyping, and the only thing that catches retyping is **statistical keystroke-cadence analytics** — probabilistic, post-hoc, false-positive-prone, and not evidenced in OnVUE.

## 1. Does OnVUE detect/log/block copy-paste in-exam (grounded; UNKNOWNs labeled)

**(a) Does Browser Lock disable paste INTO the exam, or is that a per-sponsor exam-UI setting?**
- Pearson's documented Browser Lock capability is: it "blocks other software during the exam, including Photoshop, screen capture tools, screen-sharing tools, and screen-mirroring tools. It also blocks **keyboard shortcuts that let candidates switch apps** or use software that is not allowed" [S3; T05 §2]. This names **app-switch** shortcuts — **not** in-field clipboard paste. **No Pearson document states Browser Lock disables Ctrl+V/paste into the answer field.** Status: **UNKNOWN / not documented.**
- Pearson's only clipboard statement is a **conduct rule**, not a technical control: "You may not **copy/paste** or attempt to remember test questions or test answers from the exam" [S1]; Microsoft's sponsor page echoes "You may not copy or record questions or answers" [S2]. This governs copying content **out** (exfiltration), is enforced by **policy + proctor**, and says nothing about a client-side block on pasting **in**.
- OnVUE exam content is delivered **in-browser** (sponsor exam UI on `*.starttest.com` / `*.programworkshop.com` domains, launched inside Browser Lock) [S3]. Any field-level "disable paste" therefore lives in the **sponsor's exam-delivery UI** (a `onpaste`/`beforeinput` handler on the answer field), not in Browser Lock. So whether paste-into-field works **depends on the exam sponsor's UI configuration**, and is **per-sponsor / per-exam**, not a global OnVUE guarantee. Compare the explicit analog: Respondus LockDown Browser (a different product) **does** advertise "Prevents copying and pasting anything to or from an assessment" as a core feature [S4, S5] — OnVUE makes **no** equivalent documented claim.

**(b) Any documented clipboard monitoring / copy-paste flagging in OnVUE telemetry?** **None found.** No Pearson or sponsor document describes OnVUE capturing clipboard contents, logging copy/paste events, or flagging paste bursts. Status: **UNKNOWN / undocumented.** (Do not assume it exists; equally, absence of documentation is not proof it is absent — treat as a genuine blind spot, defend by other means.)

**(c) Does OnVUE log keystrokes or input-injection?** **UNKNOWN** — carried from T05 §Gaps: "no source indicates OnVUE logs keystrokes." No source indicates input-injection / synthetic-keystroke detection either. Status: **UNKNOWN / undocumented.** Pearson publishes no telemetry schema; what analytics it runs on "testing events" is opaque (T05 §10 cites "comprehensive analytics tools that analyze … video").

**Net for Q1:** OnVUE's *documented* copy-paste posture is a **policy prohibition + human/AI behavioural review**, not a verified technical clipboard sensor. Clipboard logging, paste-into-field blocking, and keystroke logging are all **UNKNOWN**. The exam-UI (sponsor) layer — not Browser Lock — is where a real paste block would sit, and only if the sponsor configured it.

## 2. What the human proctor sees (screen unobserved)

In **this** deployment the candidate's **screen is not shared or captured** (T05 §10, corroborated: monitoring is "via your webcam and microphone" [T05 S3]; CompTIA: "proctored via a laptop webcam and laptop audio" [T05 S7]). Therefore, regarding copy-paste, the proctor sees:

- **Nothing of the on-screen act.** A clipboard copy or paste produces **no visible artifact** to a proctor who has no screen feed. There is no cursor, no menu, no field content visible to them.
- **Only the camera/mic channel:** face, hands, desk, room, audio. The proctor can catch the *physical correlates* of a manual channel — eyes repeatedly tracking to a second surface, visible typing bursts after looking off-screen, a second device, lips moving (dictation), a person off-camera — but **not** the clipboard operation itself.
- Consequence: in a no-screen deployment, **copy-paste is invisible to the human proctor as such.** Detection of paste-based insertion rests entirely on (i) the exam UI's own event handling, if any, and (ii) camera-visible behaviour — not on the proctor watching the screen. State this plainly to the owner: *the proctor cannot see a paste happen.*

## 3. Cross-Type-1-boundary clipboard: visibility + the guest-tools-vs-stealth tension

Setup: Type-1 hypervisor runs first; **OnVUE in the GUEST**, **answer LLM on the HOST**; candidate wants host→guest clipboard to paste answers into the exam.

### 3a. Can OnVUE (inside the guest) OBSERVE that pasted text ORIGINATED on the host?

**No — OnVUE cannot see across the VM boundary.** Clipboard transfer between host and guest is **not** an OS-visible "remote paste" inside the guest. Mechanically, the hypervisor's guest agent injects the host clipboard contents into the **guest OS's own local clipboard**; from inside the guest, a subsequent paste is an **ordinary local clipboard read**, indistinguishable from the candidate having copied something within the guest itself [S6, S8]. Guest-level software (OnVUE is guest-level in this model) sees only: "the local clipboard now contains text; it was pasted into a field." It has **no supported, documented channel to learn the clipboard's host origin** — that crossing happens *below* the guest OS, in the hypervisor/agent plane OnVUE does not inhabit. This is the same isolation that makes hypervisor-level malware analysis "invisible to the program under analysis" [S? Unit42 analog, cited S-list]. So the **origin of the text is not visible to OnVUE.** (What *is* potentially visible to OnVUE is the **means** of sharing — see 3b.)

### 3b. THE TENSION: shared clipboard needs guest tools, and guest tools are a VM signature

This is the crux and the owner's leverage.

- **Automatic host↔guest clipboard requires hypervisor GUEST TOOLS inside the guest.** This is a hard requirement across every mainstream hypervisor, from primary vendor docs:
  - VirtualBox: "With the Guest Additions installed, the clipboard of the guest OS can **optionally** be shared… **Disabled** is the default when creating a new VM" [S6, S7].
  - VMware: "To use the copy and paste functions with the guest OS, **you must have VMware Tools installed**" [S9].
  - SPICE/KVM: "SPICE requires that the guest OS is running the SPICE agent (**vdagent**)" for clipboard [S8]; QEMU bidirectional copy-paste additionally needs `qemu-vdagent` + the guest `spice-vdagent` [S? minimega].
  - General statement: clipboard sharing "needs guest tools running inside the VM… **console-only VMs or locked-down images** don't have one" [S10].
- **Those same guest tools are a canonical VM signature that VM-detection catches.** This is not incidental — the anti-VM literature targets exactly the clipboard-sharing tooling:
  - MITRE ATT&CK T1497.001 lists guest-tool artifacts as standard VM tells: `HKLM\SOFTWARE\Oracle\VirtualBox Guest Additions`, `vmmouse.sys`, the `vmtoolsd` process [S11].
  - MBC **B0009.010 "Guest Process Testing"** states it directly: "Virtual machines offer **guest additions that can be installed to add functionality such as clipboard sharing**. Detecting the process responsible for these tasks… is a technique employed by malware for detecting whether it is being executed in a virtual machine" [S12]. The clipboard-enabling component *is* the detection target.
  - Guest tools write predictable registry keys/services/drivers (`VBoxGuest`, `VMware Tools`, `vmtoolsd.exe`, OUI MACs 00:05:69/00:0C:29/08:00:27, `vmhgfs`/`VBoxSF` drivers) [S13, S14], all cheap to enumerate from inside the guest.
  - Hardening guidance confirms the countermeasure to VM detection is to **strip** these: "use a hardened/'detection-resistant' analysis VM where **Guest Additions artifacts are stripped**" [S13]. (This aligns with T14: "hardened guest strips guest additions.")

- **Therefore the attacker faces a genuine dilemma — cannot trivially have BOTH stealth AND convenient cross-boundary clipboard:**
  - **Path A — keep guest tools (convenient clipboard):** automatic host→guest paste works, but the guest now carries the guest-tool signatures that are precisely what VM-detection (OnVUE's documented "a virtual machine has been detected" hard block, T05 §4, and any sponsor/endpoint anti-VM check) looks for. **Highest detection risk.**
  - **Path B — strip guest tools (stealth guest, per T14):** removes the guest-tool VM signature **but also removes automatic shared clipboard** — the two are the same component. Cross-boundary clipboard reverts to a **manual channel.** **Clipboard convenience lost.**
  - You cannot cleanly keep A's convenience and B's stealth, because the convenience *is* the signature. This is the single most useful fact in T17 for the defender: **the stealth posture the VM-concealment strategy needs (T14) is mutually exclusive with the easy clipboard channel the copy-paste strategy wants.**

- **Residual MANUAL channels after stripping guest tools, and are THEY detectable by OnVUE?**
  - **Retype from a host overlay / second-screen view** (read the LLM answer off the host, type it into the guest): defeats clipboard-origin detection entirely (it's just typing). OnVUE has **no documented** way to detect this at the clipboard level; the only catch is (i) camera behaviour (eyes off-screen, typing bursts) and (ii) statistical keystroke-cadence analytics (§4) — neither evidenced in OnVUE. Cost to attacker: slow, high cognitive load, camera-visible.
  - **Shared folder / file drop** (also needs guest tools in most hypervisors — "shared folders… require… only the Guest Additions" [S6]) — so stripping guest tools **also** removes this; falls back to pre-staged files on the guest disk (a T06/T14 S0 staging problem, caught by golden-image reset, not by clipboard detection).
  - **Serial/virtio side-channel or custom paravirtual agent** (a bespoke non-standard tool to move text host→guest without stock guest additions): technically possible for a prepared attacker, but it is **custom R&D**, its own process/driver is a potential anti-VM/anti-process tell, and it is exactly the "pre-built image" worst case T14 §3 already scopes — defeated upstream by firmware/boot lockdown and golden-image reset, **not** by OnVUE clipboard detection.
  - **Net:** the manual channels are **not reliably detectable by OnVUE** as clipboard events, but they are **slow, effortful, and shift the tell to the camera and to boot/host integrity** — which is why T14's firmware/boot controls, not clipboard detection, are the right defense.

**Verdict Q3:** Inside the guest, OnVUE **cannot** observe host origin of pasted text (3a). The attacker's real constraint is **3b**: automatic cross-boundary clipboard demands guest tools, which are a VM signature; a stealth (stripped) guest loses automatic clipboard and is forced to a slow manual channel. **An attacker cannot easily have both stealth and convenient cross-boundary clipboard.** OnVUE detects neither the boundary crossing nor the manual retype at the clipboard level; the defensible controls are host-ownership controls (T14), not OnVUE clipboard telemetry.

## 4. Paste-vs-typed detection ceiling (no-VM case)

Single machine, LLM and exam side by side, candidate pastes (or retypes) answers.

- **Can a paste be distinguished from typing at all?** Only by the **web page/exam UI**, via the W3C Clipboard API `paste` event (and `clipboardData`), which exposes paste timestamp, size, and content to a page that chooses to listen [S15, S19]. This is a **page capability, not a secure-browser capability** — it would have to be implemented in the **sponsor's exam UI**, same layer as §1(a). Ordinary form hosts (Google Forms, Canvas) do **not** do this by default: "Google Forms has no clipboard access and cannot see paste events" [S18]; "ordinary Canvas does not tell an instructor whether each sentence was typed or pasted" [S19].
- **Is there evidence OnVUE does it?** **No.** No source indicates OnVUE (or a Pearson exam UI) logs or flags paste events. Status: **UNKNOWN / no evidence.**
- **The detection ceiling (why paste-event logging is weak):** the paste event **only fires when a paste action is actually invoked.** If the text is **typed** — manually, or by a tool that emits synthetic keystrokes instead of invoking paste — "the paste listener never fires… the content arrives in the editor **as if the candidate had typed it**" [S15]. So any paste-event block/log is **trivially bypassed by retyping** (or an auto-typer). This is the hard ceiling: deterministic paste detection cannot catch inserted-by-typing text.
- **What's left above the ceiling is statistical, not deterministic:** keystroke-cadence / "copy-typing" analytics that flag **unnaturally clean, uninterrupted insertion bursts** characteristic of transcribing an external answer. This is a real and growing technique — Codility's "Typing Pattern Detection" analyzes keystroke sequence/structure **post-submission** to flag retyped AI answers, explicitly a "**high likelihood, not certainty**" risk flag, on-by-default-but-per-assessment, skipping <10-line answers to limit false positives, and "**should not be used alone** as grounds for rejection" [S16]; a 2025 peer-reviewed model (CNN-Transformer on dwell/flight times) detects "copy-typing" precisely because "**security measures like disabling copy-paste**… [force answers to] be manually typed… creat[ing] subtle but detectable deviations" [S17]; keystroke-dynamics proctoring is an active research area [S? Dillon/De Marsico 2025]. **Characteristics that cap this method:** probabilistic, post-hoc (not real-time block), false-positive-prone (a fast typist from memory looks suspicious), needs human adjudication, and **content-length-gated**. **No evidence OnVUE employs it.**
- **Ceiling statement:** the best *deterministic* detection (paste events) is defeated by retyping; the best *statistical* detection (cadence) is a probabilistic risk flag, not proof, and is **unevidenced in OnVUE**. So in the no-VM case, **OnVUE provides no verified mechanism to distinguish pasted from typed answer insertion.** An owner who needs this must add it at the exam-UI or a dedicated analytics layer — and accept it is a review signal, not a gate.

## 5. Countermeasures (mapped; note which abandon no-screen-monitoring)

| # | Countermeasure | What it catches / does | Catches paste? Catches retype? | Abandons no-screen posture? | Note |
|---|---|---|---|---|---|
| 1 | **Disable paste in the exam config** (sponsor exam-UI `onpaste`/`beforeinput` handler on answer fields) | Blocks the paste **action** into the field; optionally logs attempts | Catches **paste**: yes (blocks). Catches **retype**: **no** (paste event never fires) [S15] | No | Cheapest, deterministic, owner-controllable **if the sponsor UI supports it**. Ceiling = retyping. Analog: Respondus blocks paste [S4]. |
| 2 | **Input-cadence / paste-burst analytics** (keystroke-dynamics copy-typing model) | Post-hoc **risk flag** on unnatural clean-insertion bursts | Catches **retype**: partially (probabilistic). Catches **paste**: via burst size, if paste not already blocked | No (uses keystroke timing, not screen) | Statistical, false-positive-prone, needs human review, length-gated [S16, S17]. **Not evidenced in OnVUE** — would be an added layer. Pairs with #1 (block paste → force retype → cadence flags the retype). |
| 3 | **Vendor/agent that monitors the clipboard or the host** | A host-level agent reading clipboard contents / flagging cross-app transfer | Catches **paste** within the host OS. Catches **retype**: no | No (clipboard/host telemetry, not screen) | **Defeated by the Type-1 split** — a host-side LLM + guest-side OnVUE means a guest clipboard monitor sees only the local guest paste (§3a); a host agent only exists if the owner controls the host. Requires **machine ownership** (ties to T14). Not an OnVUE-documented capability. |
| 4 | **Screen monitoring** (share/record candidate screen; AI + proctor review) | Sees the actual on-screen paste, the source window, the second app | Catches **paste** and **retype** (sees the act + the source) | **YES — abandons the no-screen-monitoring posture** | Strongest behavioural catch, but a deliberate policy reversal with privacy/scope cost. Still blind to a **host-side** LLM if only the **guest** screen is captured (the host screen is outside the guest capture) — so even screen monitoring is defeated by the Type-1 split unless the owner captures the **host**, which needs host ownership. |
| 5 | **In-person / test-center delivery** | Human + environmental control; no host/guest trickery that the center hasn't allowed | Catches both, plus removes the host-LLM channel if the machine is owned/locked | N/A (physical) | Highest assurance; this is where T14's firmware/boot lockdown + golden image live. The copy-paste problem largely dissolves when the owner controls the machine and the room. |
| 6 | **Firmware/boot lockdown + strip guest tools from the golden image** (T14 controls) | Prevents the concealed guest **and** removes guest-tool clipboard channel at the source | Removes the **convenient** cross-boundary clipboard entirely (forces slow manual retype) | No | **The leverage from §3b, operationalized:** because clipboard sharing *is* the guest-tool signature, an owned, guest-tool-free, firmware-locked image denies both VM concealment (T14) and automatic cross-boundary clipboard in one move. **Requires machine ownership** — a BYOD proctoring model cannot do it. |

**Reading of the table.** Only #4 (and a host-capturing form of it) **requires abandoning the no-screen-monitoring posture**, and even #4 is **defeated by the Type-1 host/guest split** unless the owner captures the *host* (hence needs host ownership). The owner's efficient stack is: **#1 (block paste in exam config) + #2 (cadence analytics as a review flag) as detective layers**, and **#6 (owned, firmware-locked, guest-tool-free golden image — T14) as the preventive layer that simultaneously kills the convenient clipboard channel.** Do not rely on OnVUE clipboard/keystroke telemetry — it is **UNKNOWN/undocumented** (§1), so it is a backstop at best, not a control.
