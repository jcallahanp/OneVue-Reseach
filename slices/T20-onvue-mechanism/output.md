# T20 OnVUE — how it works (mechanism dossier)

Scope: Technical synthesis of **Pearson VUE OnVUE** online-proctored delivery from the **public record only** (Pearson docs, patents, acquisitions, vendor/SDK docs, privacy disclosures, litigation, security/academic research, candidate-facing guides). No binary reverse-engineering of the OnVUE client was performed; where client internals are described they are **inferred** from documented behaviour, OS permission models, named third-party components, and reverse-engineering of *analogous* (non-OnVUE) proctoring suites. Every item is tagged **[DOC]** (documented in a cited source) or **[INF]** (inference/educated guess). All access dates **2026-11-12**. Extends T05 (control surface); does not repeat its summary table.

Key deployment anchor (from T05, re-confirmed below): in the defended deployment the **candidate screen is NOT captured/streamed** — monitoring is **webcam video + microphone audio + client-side lockdown telemetry**. OnVUE enforces the screen *locally* (Browser Lock) but does not transmit screen contents to the proctor.

---

## Architecture overview (client → stream/telemetry → backend)

**Candidate device** runs a downloaded native lockdown client (**OnVUE / Pearson VUE "Browser Lock" / "Pearson ITS Secure Browser"**, process **`proctorapp`**). The client (a) takes exclusive control of camera, microphone and input; (b) enforces single-app lockdown (blocks app-switch keys, other software, screen-capture/share/mirror, multiple displays, VMs); (c) runs the exam **test driver** (the same engine as center-based IBT delivery); and (d) captures check-in artifacts (headshot, ID photos, room scan) and the live A/V feed.

**Three outbound channels leave the device** (ports 80/443 + 1935; all must stay open — **[DOC]** Pearson PDF):
- **Media / recording** → `*.wowza.com` over **RTMP port 1935** (TCP). Wowza Streaming Engine = commercial media server that *ingests, transcodes and records* the webcam/mic feed. **[DOC]** host+port; **[INF]** that 1935→Wowza carries the exam A/V.
- **Live communications** → `*.twilio.com` (greeter/proctor video + voice; proctor can also phone the candidate, caller-ID 617-379-0635 Boston). **[DOC]** host; **[INF]** Twilio = WebRTC live comms layer.
- **Realtime signalling / state** → `*.ably.io`, `*.ably-realtime.com` (pub/sub realtime messaging: chat, presence, session events). **[DOC]** host; **[INF]** role.

**Backend / proctor plane:** `*.proctorcam.com` (the ProctorCam platform Pearson acquired in 2015 — the proctor-facing monitoring/queueing/recording system), plus Pearson delivery/identity hosts: `*.pearson.com`, `*.pearsonvue.com`, `*.pvue2.com`, `*.starttest(2).com`, `*.startpractice.com`, `*.programworkshop(2).com`, `*.gettesting.com`, `*.verifyreadiness.com`, `*.onvue.com`. **[DOC]** allowlist. Human **greeters** (check-in) and **proctors** (monitoring) sit at these backends. **AI/analytics** run server-side for ID authentication, face-to-ID comparison, and post/real-time video analysis. **ID document verification** is powered by **Regula Forensics Document Reader SDK**. **[DOC]**

Data flow, one line: *webcam/mic → RTMP/WebRTC → Wowza (record/transcode) + Twilio (live) + Ably (events) → ProctorCam/Pearson backend → human proctor + AI analytics → flag/terminate + retained recording to sponsor.*

## 1. Client architecture (secure browser / Browser Lock / `proctorapp`)

- Named **"Pearson VUE Browser Lock"** or **"Pearson ITS Secure Browser"**; the runtime process is **`proctorapp`**. **[DOC]** (Pearson PDF).
- **Delivery = download-and-run, not install.** Candidate downloads the **"OnVUE application (free to download)"**, closes all other apps (Ctrl+Alt+Del / Force Quit), then **"run the program manually"** from the download location — *"for security reasons, it will not"* auto-run. Candidate **re-downloads a fresh copy at each check-in** ("delete any previously downloaded versions"). **[DOC]** (testing guide 2024; About OnVUE 2020). **[INF]** This implies an ephemeral, per-session standalone executable/app-bundle launcher rather than a persistently-installed service — consistent with no documented uninstall step.
- **App type: native desktop app (strong [INF]).** No public teardown of the OnVUE bundle exists (confirmed: searches for a `proctorapp` bundle/Electron/CEF analysis return nothing). Native is inferred from: macOS TCC permission grants required; low-level input/display control; the "Browser Lock" rendering a web-delivered test driver. Whether the UI shell is **Chromium/CEF/Electron-based** is **plausible but [INF]/UNVERIFIED** (Electron = Node.js + Chromium is the common pattern for such clients; no OnVUE evidence).
- **macOS privilege/permission model [DOC]:** OnVUE must be granted, in System Settings > Privacy & Security: **Camera, Microphone, Automation, and Input Monitoring.** Mechanism implications **[INF]**: *Input Monitoring* ⇒ the client taps global keyboard/input events (e.g. a `CGEventTap`) to **intercept/suppress app-switch and shortcut keys**; *Automation* (Apple Events / System Events) ⇒ ability to **enumerate and act on other apps** (detect/close prohibited software). On Windows the equivalent app-switch-key blocking is a low-level keyboard hook **[INF]**.
- **Privilege level:** Pearson docs do **not** state admin rights are required. A third-party sponsor-help page claims OnVUE "requires full local administrator rights"; **UNVERIFIED by vendor**. **[DOC third-party / INF]**
- **Exclusive device control is a patented design principle** (Pearson patents, §6): the client "take[s] exclusive control of the device's camera, microphone, and biometric sensors" and can "take exclusive control of network interfaces and disable communications it doesn't need." **[DOC patent]**; that OnVUE implements exactly this is **[INF]**.
- OS support (current): **Windows 11/10 64-bit (no S Mode)**, **macOS 14+ (no beta)**; Linux/Chrome OS unsupported. Historical drift: the 2020 About-OnVUE doc cites Win 7 SP1 / macOS 10.10 and 1 Mbps up/down — current PDF requires 6/2 Mbps — i.e. requirements have tightened materially over time. **[DOC]**

## 2. Detection mechanisms — how each is implemented

*OnVUE's own detection internals are not published; Pearson exposes only error strings and policy. The "how" below pairs OnVUE's **[DOC]** observable behaviour with **reverse-engineered mechanisms from analogous (non-OnVUE) lockdown suites** — chiefly the 2022 academic study "Watching the Watchers," which RE'd Examplify, ILG Exam360, Exam4, Electronic Blue Book (**NOT** Pearson). Treat the general-class mechanisms as [INF] for OnVUE.*

- **VM detection — OnVUE behaviour [DOC]:** blocks on error *"A virtual machine has been detected. Please close all virtual machine software before continuing"*; candidate cannot continue. False positives reported from Windows **Hyper-V / VirtualMachinePlatform / WSL / Docker** even with no active VM (fix set: `wsl --shutdown`, DISM-disable those features, reboot) — indicating the check reacts to **hypervisor-platform surfaces and leftover VM drivers/devices**. **[DOC third-party/NashTech]**
  - **General-class mechanism [INF/analog-DOC]:** proctoring suites "implement a virtual machine check by **comparing the CPU vendor field** (CPUID hypervisor/vendor string) against a list of known VM vendors," plus matching against "known virtual machine software vendors" (processes/drivers). Bypassable in the analog by spoofing the CPU vendor string. ("Watching the Watchers.")
- **Prohibited-process / app enumeration — OnVUE [DOC]:** requirement "ability to close all applications except OnVUE"; Browser Lock "blocks other software during the exam, including Photoshop, screen capture tools, screen-sharing tools, and screen-mirroring tools" and "blocks keyboard shortcuts that let candidates switch apps." Windows: close apps in Task Manager > Processes and > Services.
  - **Mechanism [INF/analog-DOC]:** implemented as a **process allow-list + block-list**; the client "compare[s] the processes currently running on the system to a list … and forcibly kill[s] any processes running but not included on the list," and can drop/deny network traffic to flagged destinations. ("Watching the Watchers," re: Examplify/ILG.) Exact OnVUE enumeration/kill API is **UNDOCUMENTED**.
- **Multiple-display detection — OnVUE [DOC]:** single display required; external monitors must be unplugged/turned away **before the check-in room photos**; laptop-with-external-monitor requires lid closed. Whether the client hard-blocks at launch via OS display enumeration (EDID) vs. relying on the proctor's visual room-scan is **UNVERIFIED [INF]**; at least partially enforced at the human/room-scan stage.
- **Remote-desktop / screen-share detection — OnVUE [DOC]:** Browser Lock blocks screen-sharing and screen-mirroring tools; third-party sponsor-help states OnVUE "actively blocks remote-control software"; a candidate running Remote Utilities was prompted mid-exam to close it. Per-protocol specifics (RDP/VNC/TeamViewer) **not named** — covered by generic categories. Mechanism **[INF]**: process/driver block-list + possibly session/display API checks.
- **Virtual-camera / virtual-audio — OnVUE [DOC]:** policy prohibits **webcam filters incl. Apple "Reactions"** and phone-as-webcam; whether OnVUE *technically* detects a software virtual camera (OBS/ManyCam/Snap) is **UNDOCUMENTED**.
  - **Mechanism [INF/analog-DOC]:** analog suites detect virtual webcams/mics by **comparing the device bus location / querying a driver list against a block-list of known virtual-device vendors**; a matched virtual device blocks the exam. ("Watching the Watchers.") Independent analog testing (SETU 2026, T05) found a commercial proctoring tool did **not** distinguish physical vs OBS virtual cam at the capture-API level — i.e. this class of check is **not reliably effective**.

## 3. Check-in & identity pipeline

- **Pre-registration gate [DOC]:** candidate must accept a **"facial comparison policy agreeing to the use of artificial intelligence (AI) techniques"** before registration completes. (About OnVUE 2020.)
- **System test [DOC]:** optional pre-exam utility (same device/network) checks internet speed, mic/speaker, and that the **webcam takes a clear image of the candidate and their ID**; runs a short exam simulation.
- **Self (autonomous) check-in — artifacts captured [DOC]:** (1) test mic/webcam/audio; (2) **capture a headshot**; (3) **capture photo ID** (government-issued, original, name matches registration); (4) **room/workspace scan** — documented as **"four photos of the testing room workspace"** (2020) and, in the 2024 candidate guide, a **"full 360-degree room scan."** (Evolution: 4 stills → 360° scan.)
- **Automated validation [DOC]:** "The OnVUE software uses **artificial intelligence (AI) techniques to perform enhanced ID authentication and a face-to-ID-photo comparison.** A Pearson VUE **greeter checks the room images.**" If no issues → self check-in succeeds → candidate launches the secure exam.
- **ID-document verification vendor [DOC]:** **Regula Forensics** — the **Document Reader SDK** reads the ID photographed by the candidate, identifies document type/issuing country via **OCR + machine learning**, and matches against Regula's library (stated 10,000+ templates, 248 countries/territories, 98 languages) to detect fraudulent/proxy IDs (partnership announced 2021-07-07). Certain IDs (US DoD/CAC, Canadian Health Card, Aadhaar-restricted, etc.) cannot be camera-captured and are disallowed online.
- **Facial-comparison biometric [DOC/legal]:** OnVUE performs **face-to-ID-photo comparison** ("facial comparison," "facial geometry"). Confirmed by litigation: **Velazquez v. NCS Pearson** (Cook County 2022-CH-00280) — an Illinois **BIPA** class action over OnVUE's facial comparison, **$18,224,000** settlement, **final approval 2025-07-08**, covering Illinois OnVUE test-takers **2019-08-15 → 2023-02-01** "that may have used facial comparison." (Same case also covers palm-vein scans at physical centers.) The specific face-matching engine/vendor and whether a persistent face **template** is stored vs. live-frame-to-ID comparison is **not publicly specified [INF/UNKNOWN]**; Pearson publicly says it uses "advanced identity authentication technology from market leaders" and "several AI sensors," and that interventions remain human-led.
- **Remediated check-in [DOC]:** if automated validation fails, the session enters the **live greeter queue**; a human greeter re-verifies name/ID, visually matches the ID to the live webcam feed, and confirms the testing area is clear before handing to a proctor. Greeter/proctor queues are segmented by language/geography.
- **Identity roadmap (center-side, adjacent) [DOC]:** Pearson (Pearson Professional Assessments) uses **palm-vein** biometrics at test centers and announced a move to **palm-print** biometrics (with Redrock) for global exam authentication (Biometric Update, 2026-01). This is center-based identity, not the OnVUE online face path.

## 4. Monitoring & analytics (what IS vs ISN'T captured)

- **Captured during exam [DOC]:** **webcam video + microphone audio** only — "monitored by artificial intelligence and a Pearson VUE-certified proctor via webcam and microphone during the exam"; "you will be monitored at all times. Audio and video may be recorded." Webcam min 640×480 @10fps, head-and-shoulders, eye-level, no filters.
- **Screen NOT captured/streamed [DOC/INF]:** no Pearson privacy or technical text describes streaming candidate **screen contents**; CompTIA states OnVUE exams are "proctored via a laptop webcam and laptop audio." Screen integrity is enforced **locally** by Browser Lock and is **not observable** by the proctor. (Consistent with the defended deployment.)
- **Live human proctoring [DOC]:** certified Pearson-employed proctors observe in real time, continuously; one proctoring tier ("Live Monitoring") is standard. **"Exams are terminated immediately if prohibited behavior is detected."** Proctor↔candidate communication is **primarily via a built-in chat application**; proctor may also call the candidate's phone.
- **Automated analytics [DOC]:** Pearson's privacy policy cites "comprehensive analytics tools that analyze … video from testing sessions"; the AI performs ID authentication and face-to-ID comparison at check-in and augments live proctoring during the exam. Pearson also markets **"Deep Web" scanning for indications of test-content infringement** and a per-client "designated security analyst" with dashboards. Precise in-exam signals (gaze/head-pose/multi-face/voice-activity) are **not itemised by Pearson [INF]**; analog patents (Verificient, §6) model this class as face-count/head-orientation/motion/audio-level/keystroke feature vectors with server-side outlier clustering — **analog, not OnVUE**.
- **Recording & review workflow [DOC]:** session audio/video is recorded; managers perform **"audit of phone calls, chat records, and test session video recordings"** for QA; recordings are provided to the exam sponsor. Human proctor makes the final call on irregularities (consistent with Pearson's "human-led intervention" claim).
- **Human vs automated boundary [DOC]:** *Check-in* = AI (ID auth + face match) with greeter checking room images, escalating to a human greeter on failure. *During exam* = AI analytics + continuous human proctor; termination is proctor-driven on prohibited behaviour.

## 5. Streaming & telemetry architecture

- **Allowlist (verbatim, Pearson PDF) [DOC]:** `*.pearson.com`, `*.pearsonvue.com`, `*.proctorcam.com`, `*.programworkshop.com`, `*.programworkshop2.com`, `*.starttest.com`, `*.starttest2.com`, `*.startpractice.com`, `*.gettesting.com`, `*.verifyreadiness.com`, `*.twilio.com`, `*.pvue2.com`, `*.ably.io`, `*.ably-realtime.com`, `*.wowza.com`, `*.onvue.com`. **Ports 80 (HTTP), 443 (HTTPS), and 1935 (video streaming) must remain uninterrupted.** No VPN/proxy; TLS-inspection discouraged.
- **Wowza (`*.wowza.com`, port 1935) = media server [DOC role]:** Wowza Streaming Engine ingests **RTMP** over a persistent TCP connection on **1935**, then "transcodes, records, and repackages." **[INF]** OnVUE publishes the candidate webcam/mic feed via RTMP to Wowza for **recording + distribution to proctors** (RTMP is an ingest/contribution protocol; browsers don't play RTMP, so Wowza repackages to HLS/WebRTC for the proctor view).
- **Twilio (`*.twilio.com`) = communications [DOC host / INF role]:** live greeter/proctor interaction (WebRTC video/voice, possibly the PSTN call-out to the candidate's phone). 
- **Ably (`*.ably.io`, `*.ably-realtime.com`) = realtime messaging [DOC host / INF role]:** pub/sub transport for chat, presence, session-state and event signalling between client, proctor and backend.
- **ProctorCam (`*.proctorcam.com`) = proctor platform backend [DOC/INF]:** Pearson VUE **acquired ProctorCam (Boston) in June 2015**; ProctorCam was the "fully automated" online-proctoring product that became OnVUE's foundation and "now leverages the scale of Pearson VUE's infrastructure." The `proctorcam.com` domain + the Boston (617) proctor call-back number corroborate ProctorCam infra still underpinning the proctor-facing plane.
- **Pearson delivery/identity hosts [DOC]:** `starttest*/startpractice/programworkshop*/gettesting/verifyreadiness/pvue2/onvue.com` serve the test driver, system-test/readiness check, scheduling and result feed; the OnVUE exam uses the **same test-driver engine as center IBT delivery**.
- **Data location / processing / retention [DOC+INF]:** A/V processed through the streaming/comms stack into the ProctorCam/Pearson backend; AI runs **server-side** (patents describe back-end facial recognition and trust-scoring). Retention: biometric data kept "as long as deemed necessary by the test sponsor" (Illinois capped 3 yrs); session A/V supplied to the sponsor. A third-party FAQ cites 30-day session retention (**possibly stale/UNVERIFIED**). Encryption-at-rest of biometric data was **not clarified** in the BSB review (§6). "OnVUE adheres to local privacy and data laws in 190 countries."

## 6. Known security/privacy research, patents, incidents

**Pearson patents (documented designs; that OnVUE implements each is [INF]):**
- **US 10,977,595 B2** — Pearson Education, priority 2017-12-27, granted 2021-04-13. **Continuous identity verification**: client camera images sent to back-end facial recognition; client takes **exclusive control** of camera/mic/biometric sensors; behaviour analytics (video/keystroke/mouse), body-movement comparison vs a prior exam; a **trust score** below threshold triggers assigning an additional proctor. **[DOC]**
- **US 10,922,639 B2** — Pearson Education, priority 2017-12-27, granted 2021-02-16. **Risk/trust score** from platform history + device info + identity-matching + external records; higher trust ⇒ test-from-home, **automated greeting**, fewer checks; defines **greeter vs proctor device roles** and a **secured local network**; client can "take exclusive control of network interfaces." Mirrors OnVUE's greeter/self-check-in design. **[DOC]**
- **US 10,785,311 B2** (+ continuation app 16/998919) — Pearson Education, "Secure cloud-managed content delivery computer ecosystem": claims launching a **VM, then a nested VM**, and streaming **pixel data** to the inner VM to deliver content and collect responses. A patented **secure content-delivery** approach (not VM *detection*); relationship to shipping OnVUE is **UNVERIFIED [INF]**. **[DOC]**
- **Analog (NOT Pearson): US 8,926,335 / US 10,290,199** — **Verificient Technologies** (Proctortrack): on-device **feature-vector extraction** (face count/orientation/motion, audio level, keystroke timing) sent in preference to video; **server-side clustering (k-means) outlier detection**; escalate to video only for flagged examinees; baseline-vs-live dot-product identity match. Useful model of the *class*; **not OnVUE**. **[DOC]**

**Independent / academic analysis:**
- **"Watching the Watchers: bias and vulnerability in remote proctoring software"** (arXiv 2205.03009, 2022) — reverse-engineered **law-exam** suites (Examplify, ILG Exam360, Exam4, Electronic Blue Book — **not OnVUE**). Documents the general mechanisms cited in §2 (CPU-vendor VM check, process allow/block-lists with forced kill, virtual-cam driver/bus block-lists, static keys in binaries, variable TLS). ## 7. Documented / inferred limitations (what OnVUE structurally cannot see)

- **Screen is unobserved.** Browser Lock enforces screen state **locally**; no screen stream reaches the proctor. Anything the lockdown client fails to block on-device is **not independently visible** to a human reviewer (no screen recording to audit after the fact). **[DOC/INF]**
- **VM detection is heuristic and bypassable in principle.** The documented false-positive behaviour (Hyper-V/WSL triggers) and the analog CPU-vendor-string / known-vendor-list method imply detection keys on **observable hypervisor/CPU/driver artifacts**; the analog literature shows these can be spoofed. A **Type-1 / bare-metal hypervisor** presenting a clean guest, or VBS/HVCI/nested-virtualization handling, is **not documented** as detected. **[INF/UNKNOWN]**
- **No cross-VM / cross-device boundary visibility.** OnVUE runs inside one OS instance and sees only that instance's processes/devices/displays and the webcam frame. It cannot observe a **separate physical device**, a second person or screen **outside the camera cone**, or activity on hardware it does not control. **[INF]** (structural)
- **Virtual-camera detection depends on a driver/device block-list.** If a virtual camera is not on the list (or presents as a standard capture device), analog testing shows it can pass — i.e. feed substitution is a known weak point of this detection class. OnVUE's specific coverage is **UNDOCUMENTED**. **[INF/analog-DOC]**
- **Multi-monitor enforcement may be partly human.** Whether the client hard-blocks via EDID enumeration vs. relying on the room scan / proctor is **UNVERIFIED**; docking/mirroring edge cases exist. **[INF]**
- **Off-camera audio/visual cheating** (notes behind the camera, whispered aids, a phone just out of frame) is bounded by webcam/mic reach and proctor attention, not by the client. **[INF]**
- **Client is ephemeral/user-space (inferred).** Downloaded-and-run-manually with no documented persistent service/driver install suggests limited post-session footprint and limited kernel-level visibility vs. an installed agent. **[INF]**

## What is confirmed vs still opaque

**Confirmed (documented):** host/port allowlist and the 1935=RTMP/Wowza media path; Wowza=media server, Twilio/Ably hosts present, ProctorCam=acquired 2015 proctor platform; client named Browser Lock/ITS Secure Browser, process `proctorapp`, download-and-run-manually, re-download each session; macOS requires Camera/Mic/Automation/Input-Monitoring; full check-in pipeline (headshot → ID photo → room scan [4 photos→360°]) with AI ID-auth + face-to-ID comparison and greeter room-image review, remediated human check-in; Regula Forensics = ID-document SDK; facial-comparison biometric (BIPA/Velazquez); webcam+mic monitoring only, screen not streamed; AI + continuous certified proctor, immediate termination, chat comms, manager audit of recordings; Pearson patents for continuous ID / trust-score / greeter / exclusive device & NIC control; VM block error string + Hyper-V/WSL false-positive triggers.

**Still opaque (undocumented / inferred):** exact app framework (native confirmed by behaviour; Electron/Chromium UI unverified); exact VM/hypervisor detection method for OnVUE (only analog CPU-vendor method known); whether VBS/HVCI/nested/Type-1 are detected; admin-rights requirement (third-party claim, vendor-silent); whether OnVUE technically detects software virtual cameras/audio; per-protocol remote-desktop detection; multi-monitor hard-block vs human-catch; the specific face-matching engine/vendor and whether a persistent template is stored; in-exam AI signal set and thresholds; current authoritative A/V retention period and biometric encryption-at-rest; any OnVUE client CVE. No public binary teardown of the OnVUE client exists.
